## 1. 개요/목표

인증된 사용자별로 개인 할일(Todo)을 카테고리와 기간(시작일/종료일) 단위로 관리하는 웹 애플리케이션을 만든다.
(파생: REQ-01, REQ-02 — `docs/1-domain-definition.md` §1)

- 목표 1: 사용자별로 로그인 후 자신의 Todo만 등록/조회/수정/삭제할 수 있다. (REQ-01)
- 목표 2: Todo는 단순 마감일이 아닌 시작일~종료일 기간으로 관리되고, 상태(시작전/진행중/완료/지연)가 자동 판정된다. (REQ-02)

## 2. 목표 사용자

- 학생, 20~50대 직장인. 개인 할일/일정을 카테고리로 나눠 관리하고 싶은 일반 사용자.
- 별도 페르소나 시나리오는 작성하지 않음(범위 외).

## 3. 범위

### In-scope (도메인 정의서 UC-01~UC-08 기반, PRD 기능 ID는 FR-01~FR-08)

- 회원가입, 로그인/인증 (FR-01, FR-02)
- 회원정보 수정(본인) (FR-03)
- 카테고리별 할일 등록, 카테고리 미지정 시 '기본' 자동 적용 (FR-04)
- 할일 등록 시 시작일/종료일 캘린더 선택 (FR-05)
- 할일 목록 조회 및 필터링(카테고리별/상태별) (FR-06)
- 할일 수정 (FR-07)
- 할일 삭제 (FR-08)
- 반응형 웹 UI (PC/모바일 브라우저 대응)

### Out-of-scope (도메인 정의서 §9 반영)

- SNS/소셜 로그인 등 외부 인증 연동
- 첨부파일 업로드/관리
- 네이티브 모바일 앱 (iOS/Android)
- 접근성(a11y) 대응
- 알림/리마인더, 협업(공유·초대) 기능, 통계/리포트 — 도메인 정의서 UC 범위에 없으므로 제외

## 4. 기능 요구사항

PRD의 기능 ID는 FR-01~FR-08을 사용한다(도메인 정의서 UC-ID와 1:1 대응, "도메인 UC" 열 참조). 각 기능에 적용되는 BR(비즈니스 규칙)을 명시한다.

| 기능 ID | 도메인 UC | 기능명                    | 설명                                                                                | 적용 규칙                                                                                                                         |
| ------- | --------- | ------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| FR-01   | UC-01     | 회원가입                  | email/password/name으로 계정 생성. 미인증 상태에서 접근 가능한 유일한 화면 중 하나. | BR-01(미인증 접근 허용), BR-02(email unique), BR-09('기본' Category 자동 생성)                                                    |
| FR-02   | UC-02     | 로그인                    | email/password로 인증, 세션/토큰 발급. 이후 모든 API는 인증 필요.                   | BR-01(그 외 전 기능 인증 필수, 미인증 401)                                                                                        |
| FR-03   | UC-03     | 회원정보 수정             | 로그인한 본인의 name 등 정보 수정.                                                  | BR-06(소유권), BR-07(본인만 가능)                                                                                                 |
| FR-04   | UC-04     | 카테고리별 할일 등록      | 카테고리 지정하여 Todo 생성. 미지정 시 서버가 '기본' 카테고리 자동 적용.            | BR-03(기본 카테고리 자동적용), BR-04(카테고리 소유권/존재 검증), BR-05(startDate<=endDate), BR-08(기본 카테고리 삭제 불가/재배정) |
| FR-05   | UC-05     | 시작일/종료일 캘린더 선택 | Todo 등록 폼에서 캘린더 UI로 startDate/endDate 선택(날짜 단위, 시각 없음).          | BR-05(startDate<=endDate)                                                                                                         |
| FR-06   | UC-06     | 할일 목록 조회/필터링     | 본인 Todo 목록을 카테고리별 및 상태(시작전/진행중/완료/지연)별로 필터링 조회.       | BR-06(소유권), §5 상태 판정 규칙                                                                                                  |
| FR-07   | UC-07     | 할일 수정                 | 본인 소유 Todo의 title/category/기간/완료여부 수정.                                 | BR-04, BR-05, BR-06                                                                                                               |
| FR-08   | UC-08     | 할일 삭제                 | 본인 소유 Todo 삭제.                                                                | BR-06                                                                                                                             |

참고: 카테고리 CRUD(생성/이름변경) 자체는 FR-04(등록 시 카테고리 선택)에 포함되는 부속 기능으로 취급하며, '기본' 카테고리는 회원가입 시 자동 생성되고(BR-09) 삭제 불가(BR-08).

## 5. 비기능 요구사항

### 성능/확장성 (동시접속 1000명 목표)

- API 평균 응답 시간 300ms 이하(목록 조회 기준), p95 800ms 이하.
- PostgreSQL 커넥션 풀(pg Pool) 사용, 앱 인스턴스당 max 20 커넥션 수준으로 시작(추후 튜닝).
- 인덱스: `todo(userId)`, `todo(userId, categoryId)`, `category(userId)`, `user(email)` unique index. 목록 조회는 userId 기준 인덱스로 필터링 후 애플리케이션 레벨에서 상태(파생값) 필터링.
- 상태(status)는 저장 컬럼이 아닌 파생 계산(§5 도메인 정의서)이므로 DB 인덱스 대상이 아님 — 필요 시 startDate/endDate 인덱스로 보완.

### 반응형 UI

- 브레이크포인트: mobile < 640px, tablet 640~1024px, desktop > 1024px (Tailwind 기본값 기준, 커스텀 CSS 프레임워크 도입 없이 CSS media query로 대응).
- 모바일 전용 네이티브 앱 없음 — 반응형 웹 하나로 전 디바이스 대응.

### 보안

- password는 해시 저장(평문 금지, 도메인 정의서 §3.1).
- 인증 필요 API는 401, 소유권 위반은 403 (BR-01, BR-06).
- 인증 방식: JWT. access token(단기, 예: 15분)과 refresh token(장기, 예: 7일)을 함께 발급한다.
  - access token: API 요청 시 `Authorization: Bearer` 헤더로 전달, 만료 시 401.
  - refresh token: access token 재발급 전용. 별도 저장(HttpOnly 쿠키 권장) 후 `/api/auth/refresh`로만 사용, 탈취 시 피해 범위를 access token보다 좁게 유지하기 위해 클라이언트 JS에서 직접 접근 불가하도록 한다.

### 접근성

- 별도 a11y 대응 없음(범위 외, 명시적 고지).

## 6. 기술 스택 및 아키텍처

- 프론트엔드: React 19 + TypeScript, Zustand(클라이언트 전역 상태: access token 등 인증 상태/UI 상태), TanStack Query(서버 상태 fetch/캐시/동기화 — Todo/Category/User 데이터). access token 만료(401) 시 TanStack Query 에러 핸들링에서 refresh 후 재요청.
- 백엔드: Node.js + JavaScript + Express, DB 접근은 `pg` 라이브러리로 직접 SQL 작성(ORM 미사용 방침 — 쿼리는 파라미터 바인딩(`$1,$2..`)으로 SQL 인젝션 방지, 재사용 쿼리는 함수로 모듈화). 인증은 JWT(access/refresh token) 기반, 세션 저장소 없이 stateless 처리.
- DB: PostgreSQL 17.
- API 문서: `backend/swagger.json`(OpenAPI 3.0) + `swagger-ui-express`로 개발환경(`NODE_ENV=development`)에서만 `/api-docs` 노출. 운영환경에서는 비활성화.
- 배포/아키텍처: 단일 Express 서버(REST API) + React SPA(정적 빌드 서빙 또는 별도 호스팅), Stateless API + pg Pool로 수평 확장 대비.

## 7. API 개요 (엔드포인트 수준, 상세 스펙 아님)

| Method | Endpoint            | 설명                                         | FR           |
| ------ | ------------------- | -------------------------------------------- | ------------ |
| POST   | /api/auth/register  | 회원가입                                     | FR-01        |
| POST   | /api/auth/login     | 로그인, access token + refresh token 발급    | FR-02        |
| POST   | /api/auth/refresh   | refresh token으로 access token 재발급        | FR-02        |
| POST   | /api/auth/logout    | refresh token 무효화                         | FR-02        |
| GET    | /api/users/me       | 내 정보 조회                                 | FR-03        |
| PATCH  | /api/users/me       | 내 정보 수정                                 | FR-03        |
| GET    | /api/categories     | 내 카테고리 목록                             | FR-04        |
| POST   | /api/categories     | 카테고리 생성                                | FR-04        |
| DELETE | /api/categories/:id | 카테고리 삭제('기본' 제외, 소속 Todo 재배정) | FR-04        |
| GET    | /api/todos          | 내 Todo 목록 (쿼리: categoryId, status)      | FR-06        |
| POST   | /api/todos          | Todo 생성                                    | FR-04, FR-05 |
| PATCH  | /api/todos/:id      | Todo 수정                                    | FR-07        |
| DELETE | /api/todos/:id      | Todo 삭제                                    | FR-08        |

인증: 로그인 시 access token + refresh token 동시 발급(JWT). 이후 모든 요청은 access token 필요(BR-01). access token 만료 시 401 → `/api/auth/refresh`로 재발급. 미인증 401, 타인 리소스 403(BR-06).

## 8. 일정 계획 (1인 개발, 2일)

### 1일차 (핵심 데이터/인증 완성)

- DB 스키마 설계 및 마이그레이션 (User/Category/Todo, 인덱스, unique 제약)
- 백엔드: 인증(회원가입/로그인, 비밀번호 해시, 토큰 발급), User/Category/Todo API 전체(CRUD)
- 프론트: 프로젝트 셋업(React 19+TS+Zustand+TanStack Query), 로그인/회원가입 화면, 인증 상태 연동

### 2일차 (Todo 기능 완성 + 마무리)

- 프론트: Todo 목록/필터링 화면, Todo 등록/수정 폼(캘린더 선택), 상태 뱃지(시작전/진행중/완료/지연) 표시
- 반응형 레이아웃 적용(모바일/데스크톱)
- 통합 테스트(주요 유스케이스 수동 검증), 버그 픽스, 배포

## 9. 리스크 및 가정

| 리스크/가정                                     | 내용                                                                                 |
