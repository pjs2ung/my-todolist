## 1. 개요

본 문서는 `docs/2-prd.md`의 FR-01~FR-08을 사용자 행동 흐름으로 구체화한다. 목표 사용자(학생, 20~50대 직장인)는 개별 페르소나로 창작하지 않고 "사용자"로 통칭한다(PRD §2 범위 결정 존중). 각 시나리오는 사전조건/기본흐름/예외흐름/사후조건으로 구성하며, 관련 BR-xx(도메인 정의서 §6)를 명시한다.

---

## 2. SC-01 회원가입 (FR-01)

**사전 조건**: 사용자는 미인증 상태다. 사용할 이메일로 가입된 계정이 없다.

**기본 흐름**
1. 사용자가 회원가입 화면에 진입한다(BR-01, 미인증 접근 허용).
2. email, password, name(1~50자)을 입력하고 제출한다.
3. 서버가 email unique 여부(BR-02)를 확인하고 password를 해시하여 User를 생성한다.
4. 서버가 해당 사용자의 '기본' Category를 자동 생성한다(BR-09).
5. 회원가입 완료, 로그인 화면으로 이동한다.

**예외/대안 흐름**
- E1. 이미 가입된 email 입력 시: 서버가 등록을 거부하고 "이미 사용 중인 이메일" 에러를 반환한다(BR-02). 사용자는 email을 수정 후 재시도한다.
- E2. name/password 등 필수값 누락 또는 형식 위반(name 길이 등): 서버가 400과 함께 필드별 에러를 반환한다.

**사후 조건**: User 계정과 '기본' Category가 생성된다. 사용자는 아직 로그인되지 않은 상태다.

---

## 3. SC-02 로그인 및 토큰 갱신 (FR-02)

**사전 조건**: 유효한 계정(email/password)이 존재한다.

**기본 흐름**
1. 사용자가 로그인 화면에서 email/password를 입력한다(BR-01, 미인증 접근 허용).
2. 서버가 인증에 성공하면 access token(단기)과 refresh token(장기)을 발급한다(PRD §5 보안).
3. 클라이언트는 access token을 Zustand 상태로 보관하고, refresh token은 HttpOnly 쿠키로 저장한다.
4. 사용자는 이후 모든 API 요청에 `Authorization: Bearer <access token>`을 사용한다.
5. 로그인 성공 후 Todo 목록 화면으로 이동한다.

**대안 흐름 — access token 만료 시 자동 갱신**
1. 사용자가 API를 호출했으나 access token이 만료되어 401을 수신한다.
2. TanStack Query 에러 핸들러가 `/api/auth/refresh`를 호출하여 새 access token을 발급받는다.
3. 원래 요청을 새 access token으로 재시도한다.
4. 사용자는 재로그인 없이 작업을 계속한다.

**예외/대안 흐름**
- E1. 잘못된 password 입력: 서버가 401을 반환하고 "이메일 또는 비밀번호가 올바르지 않습니다" 메시지를 표시한다(계정 존재 여부 노출 방지를 위해 email/password 오류를 동일 메시지로 처리).
- E2. refresh token도 만료/무효(로그아웃 등으로 폐기됨): `/api/auth/refresh`가 401을 반환하고, 클라이언트는 로그인 화면으로 강제 이동시킨다(재로그인 필요).
- E3. 존재하지 않는 email로 로그인 시도: E1과 동일하게 처리한다.

**사후 조건**: 사용자는 인증된 상태이며 access/refresh token을 보유한다. 이후 요청은 BR-01에 따라 인증 필요.

## 4. SC-03 회원정보 수정 (FR-03)

**사전 조건**: 사용자는 로그인(인증)된 상태다.

**기본 흐름**
1. 사용자가 내 정보 화면에서 `GET /api/users/me`로 현재 정보를 조회한다.
2. name 등을 수정하고 저장을 요청한다(`PATCH /api/users/me`).
3. 서버는 토큰의 사용자 본인 정보만 수정 가능함을 확인하고(BR-07) 반영한다.
4. 수정 완료 메시지를 표시한다.

**예외/대안 흐름**
- E1. access token 만료: 401 수신 → SC-02 대안 흐름(자동 갱신)으로 처리 후 재시도.
- E2. name 형식 위반(1~50자 초과/미달): 400과 함께 검증 에러 반환.

**사후 조건**: 본인 User 레코드의 정보가 갱신된다(updatedAt 갱신). 타 사용자 정보는 영향받지 않는다(BR-06).

## 5. SC-04 카테고리별 할일 등록 (FR-04, FR-05)

**사전 조건**: 사용자는 로그인된 상태이며 최소 '기본' Category를 보유한다.

**기본 흐름**
1. 사용자가 할일 등록 화면에 진입, `GET /api/categories`로 본인 카테고리 목록을 불러온다.
2. title(1~100자)을 입력하고 카테고리를 선택한다.
3. 캘린더 UI로 startDate, endDate를 선택한다(날짜 단위, 시각 없음)(FR-05).
4. 등록을 제출하면 서버가 categoryId 소유권/존재(BR-04) 및 startDate <= endDate(BR-05)를 검증한 뒤 Todo를 생성한다.
5. 목록 화면에 새 Todo가 나타난다.

**대안 흐름 — 카테고리 미지정**
1. 사용자가 카테고리를 선택하지 않고 등록을 제출한다.
2. 서버가 해당 사용자의 '기본' Category id를 자동 적용하여 Todo를 생성한다(BR-03).

**예외/대안 흐름**
- E1. startDate > endDate 입력: 서버가 등록을 거부하고 "종료일은 시작일 이후여야 합니다" 에러를 반환한다(BR-05). 캘린더 UI에서도 endDate를 startDate 이전으로 선택 못 하도록 1차 방지 가능.
- E2. 존재하지 않거나 타인 소유의 categoryId 전달(예: 위변조된 요청): 서버가 거부하고 에러를 반환한다(BR-04).
- E3. title 누락/길이 초과: 400 반환.
- E4. access token 만료: SC-02 자동 갱신 흐름으로 처리 후 재시도.

**사후 조건**: 새 Todo가 생성되며 isDone=false, 상태는 §5 규칙에 따라 파생 판정(시작전/진행중)된다.

---

## 6. SC-05 할일 목록 조회/필터링 (FR-06)

**사전 조건**: 사용자는 로그인된 상태이며 1개 이상의 Todo를 보유한다(없어도 빈 목록 조회는 가능).

**기본 흐름**
1. 사용자가 Todo 목록 화면에 진입, `GET /api/todos`로 본인 Todo 전체를 조회한다(BR-06, 본인 소유만 반환).
2. 서버/클라이언트가 각 Todo의 startDate/endDate/isDone과 오늘 날짜를 비교해 상태(완료/시작전/진행중/지연)를 파생 판정한다(도메인 정의서 §5).
3. 목록에 상태 뱃지와 함께 표시된다.

**대안 흐름 — 카테고리별 필터링**
1. 사용자가 특정 카테고리를 선택한다.
2. `GET /api/todos?categoryId=...`로 재조회, 해당 카테고리 소속 Todo만 표시된다.

**대안 흐름 — 상태별 필터링 (시작전/진행중/완료/지연 각각)**
1. 사용자가 상태 필터(예: "지연")를 선택한다.
2. `GET /api/todos?status=overdue`로 재조회, isDone=false이고 endDate < 오늘인 Todo만 표시된다.
3. 동일한 방식으로 "시작전"(오늘 < startDate), "진행중"(startDate <= 오늘 <= endDate), "완료"(isDone=true)를 각각 선택하면 해당 조건에 맞는 Todo만 표시된다.

**예외/대안 흐름**
- E1. Todo가 하나도 없거나 필터 조건에 맞는 항목이 없음: "할일이 없습니다" 빈 상태 화면을 표시한다(에러 아님).
- E2. access token 만료: SC-02 자동 갱신 흐름으로 처리 후 재조회.

**사후 조건**: 화면에는 본인 소유 Todo만 필터 조건에 맞게 표시된다. 타인 Todo는 노출되지 않는다(BR-06).

## 7. SC-06 할일 수정 (FR-07)

**사전 조건**: 사용자는 로그인된 상태이며 수정 대상 Todo가 본인 소유로 존재한다.

**기본 흐름**
1. 사용자가 목록에서 Todo를 선택해 수정 화면에 진입한다.
2. title/category/startDate/endDate/isDone 중 원하는 값을 변경한다.
3. 저장을 요청하면(`PATCH /api/todos/:id`) 서버가 소유권(BR-06), categoryId 유효성(BR-04), startDate<=endDate(BR-05)를 검증 후 반영한다.
4. 목록/상세 화면에 변경 사항이 반영되고 상태 뱃지도 재계산된다.

**예외/대안 흐름**
- E1. 타인 소유 Todo의 id로 수정 시도(URL 직접 조작 등): 서버가 403을 반환한다(BR-06).
- E2. 존재하지 않는 Todo id: 404 반환.
- E3. 수정 시 startDate > endDate가 되는 값 입력: 등록 시와 동일하게 거부(BR-05).
- E4. 존재하지 않거나 타인 소유 categoryId로 변경 시도: 거부(BR-04).
- E5. access token 만료: SC-02 자동 갱신 흐름으로 처리 후 재시도.

**사후 조건**: 해당 Todo의 필드가 갱신되고(updatedAt 갱신), 상태는 §5 규칙에 따라 재파생된다. 타 사용자 Todo는 영향받지 않는다.

---

## 8. SC-07 할일 삭제 (FR-08)

**사전 조건**: 사용자는 로그인된 상태이며 삭제 대상 Todo가 본인 소유로 존재한다.

**기본 흐름**
1. 사용자가 목록/상세 화면에서 삭제를 요청한다(`DELETE /api/todos/:id`).
2. 확인 다이얼로그에서 삭제를 재확인한다.
3. 서버가 소유권(BR-06)을 검증한 뒤 Todo를 삭제한다.
4. 목록에서 해당 Todo가 사라진다.

**예외/대안 흐름**
- E1. 타인 소유 Todo id로 삭제 시도: 서버가 403을 반환한다(BR-06).
- E2. 존재하지 않는(이미 삭제된) Todo id: 404 반환.
- E3. access token 만료: SC-02 자동 갱신 흐름으로 처리 후 재시도.

**사후 조건**: 해당 Todo가 영구 삭제된다. 소속 Category나 다른 Todo에는 영향이 없다.
